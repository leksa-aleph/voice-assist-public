## 1. Почему старая версия перегружала компьютер

### Причина 1 - холостое ожидание потоков PyTorch (главная)

Silero VAD зовётся 31 раз в секунду на каждый источник с тензором из
512 отсчётов. Пул потоков torch по умолчанию занимает все ядра, и между
вызовами потоки не засыпают, а крутятся в ожидании (OpenMP spin-wait).

| Замер (`tools/bench/vad_cpu.py`, 2 источника, реальный темп) | CPU |
|---|---|
| потоки по умолчанию (6) | **501%** одного ядра |
| 1 поток | 2% |
| 2 потока + `OMP_WAIT_POLICY=PASSIVE` | 4% |

Полезная работа одинаковая - 0.4 мс на вызов. Ошибка была и в старой
версии.

Весь конвейер (одна дорожка, GigaAM тоже на CPU, `tests`-скрипт с
реальным темпом):

| Настройка | CPU | Скорость STT |
|---|---|---|
| было: потоки по умолчанию | **747%** | ×20 |
| 1 поток | 69% | ×9 |
| **сейчас: 2 потока + PASSIVE** (уже в `engine._ensure_torch`) | **122%** | ×10 |

На машине с видеокартой GigaAM уходит на GPU, и CPU остаются единицы
процентов. **Сделано**: `OMP_WAIT_POLICY=PASSIVE`, `KMP_BLOCKTIME=0`,
`torch.set_num_threads(1 на GPU / 2 на CPU)`, `set_num_interop_threads(1)`.
Для старой сборки достаточно тех же строк перед `import torch`.

### Причина 2 - черновики перераспознают фразу с начала

GigaAM не потоковая: каждый черновик (раз в 0.5-0.8 с) прогоняет весь
буфер фразы заново. На 12-секундной фразе это ~20 прогонов и ~120 с
обработанного звука вместо 12 - нагрузка растёт квадратично от длины
фразы. Это же даёт скачки текста (см. раздел 3).

### Причина 3 - RNNT-декодер пошаговый

`model._decode` - Python-цикл по кадрам (40 мс) с несколькими мелкими
вызовами predictor/joint. На CPU это 12-19% времени (`tools/bench/rnnt_split.py`),
на GPU кодировщик ускоряется в десятки раз, а цикл - нет: там он станет
основной тратой и забивает очередь мелкими запусками ядер (на ROCm дорого).

### Причина 4 - тяжёлый стек

PyTorch + ROCm/CUDA + pyannote + lightning: сборка ~5 ГБ, видеопамять
~1.5-2 ГБ под контекст torch (отбирается у игр), долгий старт.

### Замеры готовых ONNX-моделей (onnx-asr 0.12, 1 поток, без spin)

`tools/bench/onnx_asr_compare.py` на 2 минутах монолога из ролика,
куски по 6 с, целиком с препроцессором и декодером:

| Вариант | Скорость | Расхождение с RNNT fp32 |
|---|---|---|
| **RNNT int8** | **×15.6** | **1.5%** слов |
| RNNT fp32 | ×11.6 | - |
| CTC int8 | ×15.9 | 12.0% |
| CTC fp32 | ×11.9 | 11.3% |

**Решение: GigaAM v3 e2e RNNT int8.** CTC на CPU не быстрее, хуже по
тексту и выдумывает английские фразы на музыке («Igl stix. What now.»).
int8 от istupakov точнее моего экспорта (1.5% против 2.7%) и меньше
(214 МБ против 304) - брать его.

Silero VAD v6 ONNX, все источники одним батчем (`tools/bench/vad_onnx.py`):
**1.3% одного ядра на 1-2 дорожки, 1.7% на 6** (было 501% на две).

Оценка целевой нагрузки: распознавание ×15 на ядро значит ~6.5% ядра
на секунду речи; с окном LocalAgreement (~1.5-2× пересчёта) - 10-13%
ядра, пока кто-то говорит, и ~2% в тишине.

## 3. Скачки субтитров - что ловит `tools/subtitle_jumps.py`

Скрипт гоняет движок на файле в реальном темпе, проигрывает события через
настоящую логику оверлея и пишет отчёт + таймлайн «что видел человек».

Базовая линия (CPU, PyTorch):

| Метрика | Discord, 3 мин | Монолог из ролика, 4 мин | Цель |
|---|---|---|---|
| слов в строке при первом появлении (медиана / макс) | 1 / 4 | **7 / 16** | ≤ 2 / 4 |
| обновлений с 5+ новыми словами разом | 10 | **35** | 0 |
| максимум слов за одно обновление | 17 | **20** | ≤ 4 |
| переписано уже показанных слов | 35% | **38%** | ≤ 10% |
| разрезов посреди мысли | 1 | 3 | 0 |
| новых карточек | 36 на 41 фразу | 24 на 26 | только при смене человека или паузе > 3 с |
| задержка первого слова (медиана / p90) | 0.42 / 1.05 с | **2.41 / 3.91 с** | ≤ 0.6 / 0.9 с |

Монолог - худший случай: длинная речь без пауз, черновики не
успевают (каждый пересчитывает всю фразу), планировщик выбрасывает
устаревшие, и первое, что видно, - сразу 7-16 слов через 2-4 секунды.
На 12-й секунде фраза режется («стилистика как будто» | «PS1, но выглядит»).

Откуда скачки (видно в таймлайне):
1. Черновик перераспознаёт фразу целиком - модель с новым контекстом
   переписывает хвост: «+17 слов» в одном обновлении.
2. Фраза длиннее 12 с режется, хвост уходит новой фразой и новой карточкой.
3. Подпись говорящего у `mon` прыгает (голос А / голос Б / ?), а склейка
   карточек работает только при одинаковом имени и не для «?» -
   каждая реплика того же человека открывает новую карточку.

## 4. Целевая архитектура и порядок работ

### Шаг 1. ONNX вместо PyTorch
- `tools/export_onnx.py` (только для разработки): GigaAM v3 e2e RNNT ->
  `models/onnx/encoder.int8.onnx` (dynamic int8 только MatMul/Gemm -
  ConvInteger в ORT CPU не поддержан; попробовать per-channel ради точности),
  `decoder.onnx`, `joint.onnx`, препроцессор (mel) в ONNX или numpy;
  WeSpeaker ResNet34 -> `speaker.onnx`; Silero v6 ONNX.
- `asr_onnx.py`: препроцессор, кодировщик, жадный RNNT в numpy с батчами,
  на выходе текст + время каждого слова (кадр × 40 мс).
- Сессии ORT: `intra_op_num_threads=1`, `inter_op=1`, `ORT_SEQUENTIAL`,
  `session.intra_op.allow_spinning=0`. Провайдер: CPU, галочка «видеокарта» -
  DirectML.
- Убрать torch/torchaudio/pyannote/gigaam/lightning из зависимостей
  рантайма; одна сборка вместо AMD/NVIDIA.

### Шаг 2. Потоковая политика вместо перераспознавания (LocalAgreement)
- Каждые ~0.4-0.5 с нового звука декодировать только окно
  `[граница_подтверждённого - 1.5 с контекста, сейчас]`, не больше ~8 с.
- Слова, совпавшие в двух гипотезах подряд и закончившиеся раньше
  `сейчас - 0.6 с`, подтверждаются и больше не пересчитываются;
  граница сдвигается по таймстемпу последнего подтверждённого слова.
- Хвост после окна контекста - заглавную/точку на стыке убирать, если
  подтверждённый текст не кончается концом предложения.
- Итог: нагрузка ограничена длиной окна, текст растёт слева направо,
  лимит 12 с больше не режет мысль.

### Шаг 3. Подача в оверлее
- Две части строки: подтверждённая (обычная) и черновой хвост (тусклее).
- Очередь показа в темпе чтения: 3-8 слов/с с ускорением при отставании;
  за кадр не больше 2-3 новых слов.
- Одна карточка на непрерывную речь источника: продолжаем ту же, пока
  пауза < 3 с, даже если подпись дрогнула; новая - при уверенной смене
  человека. Длинная карточка ограничена N строками, старые строки плавно
  уезжают вверх внутри неё.
- Гистерезис подписи говорящего у `mon`.

### Шаг 4. Стоимость интерфейса
- Часы анимации не выше 60 к/с; в покое никаких непрерывных анимаций;
  оверлей перерисовывается только при изменениях.

### Шаг 5. Проверка
- `tools/subtitle_jumps.py` до/после на трёх записях: разговор в Discord,
  монолог из видео, шумная игра.
- Цели нагрузки: тишина при включённой записи < 3% одного ядра; речь,
  один источник < 15% (CPU-режим); четыре участника через бота < 40%;
  STT ≥ ×20 на поток; RAM < 1 ГБ; видеопамять 0 в CPU-режиме.

## 5. Дизайн (после работы над нагрузкой)
- Цвет: графитовая основа + основной оттенок для выбора и интерактива
  + второй для «слушаю / в эфире». Предложить 2-3 пары на выбор.
- Иерархия текста вместо «кучки»:
  - заголовок экрана 15/600;
  - подпись группы 11px капсом, разрядка 0.8, тусклая, над карточкой;
  - строка настройки: название 14/500 + пояснение 12/400 второй строкой,
    значение или переключатель справа;
  - подписи под крупными элементами 13/400;
  - числа (задержка, таймер) - моноширинные цифры.
- Настройки - карточки со строками и тонкими разделителями (как в
  настройках Windows 11), сетка 8 px, на экране одна главная вещь.
